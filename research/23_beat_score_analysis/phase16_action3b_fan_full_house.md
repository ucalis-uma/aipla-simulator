## 1. 結論（25/25 の全一致で確定）

**レーン別スコアボーナスの決まり方は会場が満員かどうかで切り替わる:**

```
来場合計 >= 会場キャパ（満員）     → 全レーンのボーナス = f(capacity / 5)   …「※最大」そのもの
来場合計 <  会場キャパ（空席あり） → そのレーンの来場数で引く f(lane_fans)
```

| 仮説 | 一致 | 不一致 |
|---|---|---|
| 素朴な「レーン別来場数の表引き」のみ（アクション3 の結論） | 12/25 | **13/25** |
| 上記「満員一律」ルール | **25/25** | **0/25** |

- S1・S3・S4 は**来場合計 == 会場キャパの満員** → 全レーン同一（= ※最大）
- S2・S5 は**空席あり** → レーン別の値がそのまま表引きと一致
- → アクション3 の「ボーナスはレーン別」は**空席がある会場のみ**成立。満員の会場では
  レーン別来場数がいくら偏っていてもボーナスは一律（＝現行エンジンの「レーン平均」適用が偶然ちょうど正しく、
  アクション3 の §5-2 で提案した `lane_fans[]` を**無警戒に実装すると S1/S3/S4 を壊す**）

### 読み取りの自己検証（スクショ OCR を信用してよいか）

S2・S5 の 10 レーンは**来場数（5値）と表示ボーナス（5値）が独立した 2 つの行**なのに、
どちらもマスタ表引きと 1 の位（0.1pp）まで一致し、かつ単調（10,782→51.5 < 11,290→52.5 <
11,817→53.6 < 13,835→57.6 = 13,840→57.6）。誤読が 5/5 の完全一致を作る確率は実質ゼロなので、
**S2/S5 の行の読み取りは確定**。S3/S4 も「全レーン同一 = `f(cap/5)`」という内部整合（来場合計が
キャパと 1 人単位で一致）を満たしており、読み取りは健全と判断する。

## 3. 計算機への含意

1. **`lane_fans[]` 実装には必ず満員ガードを付ける**（`build.ts:728` の 1 値差し替えを配列化する際）:
   `lane_fans` の合計 `>= maxCapacity` なら**全レーン `f(cap/5)`**、そうでなければ `f(lane_fans[i])`。
   ガードなしで S3 にレーン別表引きを適用すると L5 が **−3.3pp（係数 −2.4%）**、L3 が **+1.3pp（+0.9%）**
   の誤りになる（現行の一律 +37.5% は**実機と完全一致**なので明確な後退）。S1 も L1-L3 が +0.1% 化して
   0.1pp（約 0.01%）の下振れ。
2. **得をするのは空席がある会場だけ**。S2 は平均代表値から ±1.60%、**S5 は ±2.01%**（レーン別係数の
   最大/最小 1.0403）なので、S5 相当（充足率 77%）でレーン別に切り替えるとレーン別の相対精度が最大 2% 改善する。
   合計スコアは平均が代表値として優秀なのでほぼ不変（アクション3 §3 と同じ結論）。
3. **S3 のレーン別スコア乖離は fan では説明できない**（確定）: S3 は全レーン +37.5% で一律なので、
   S3 のレーン別 `pop/sim` のばらつきの原因にはならない。fan を原因から除外できたのは本報告の成果。
4. アクション3 §4-1 の未解決点（解析トレースの `fan` 欄が表引きより 0.6〜1.9% 低い:
   S3 1361‰ vs 1375‰）**は本報告では未解明**。満員一律ルールでも説明できない
   （満員なら 1375‰ 一律のはずなので、トレース側の出所が別）。レーン別 fan を実装する前に解くこと。

## 4. 【Estimate】として残す部分（機構は未確定）

満員時に一律になる**理由**は複数区別できない:
(a) 会場が埋まった時点で全レーンが `cap/5` まで埋まったとして算定
(b) ボーナス算定が会場単位（`来場合計/5`）で行われ、満員のときだけ `cap/5` と一致
S2/S5 で空席時にレーン別が効くので (b) は単独では成立しない（満員でも空席でもない会場で
`来場合計/5` はレーン別値と一致しないはず）。(a) が最も整合的だが、
**満員かつレーン別来場が偏ったサンプル（S1/S3/S4）では両者が同一値になるため観測的に区別不能**。
実装上は §3-1 のガードで十分（区別が必要になるのは「キャパ超えの来場」が出るケースのみ）。
