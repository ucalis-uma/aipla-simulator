## 3. E0 — A/SP ノートのレーン別 implied rand（本検証による新規実行）

### 3.1 方法

トレースは NeutralRng（乱数 1000 固定）で生成されているため、`gainedScore` は乱数 1000
基準の確定値。実機ポップには実機乱数 r が乗るので **implied rand = pop / gainedScore ×
1000** で直接復元できる（K/M 表示の下限値性を考慮し、真値区間 [pop, pop+unit) から
implied 区間を出して [950,1050] との整合を判定。A スキルはフォト a_score fixed の平坦
加算がポップとトレース双方に乗るため、乗算部だけで比較）。crit は pop・gained 双方に
係数済みで処理上は無害（S2 6 セル・S3 3 セル含む）。

## 4. H4-a の前提に関する注意（頁の近似式の限定）

頁の H4-a 予測式 `pred = off/(own+off) × (liveMult_own − 1000)` は「**sim は own 属性に
しか liveMult を掛けていない**」前提の近似だが、実際のエンジン（engine.ts settleBeatNote・
gen recompute も同型）は **off 属性にも各属性自身の liveMult を掛けている**
（S2 L1 のスナップショットでは visual_up 5 段が L1 自身の visual 成分に乗っている等）。
したがって:

- 頁の式は「own liveMult を off にも足す」効果の**下限近似**として S3 の数値（+41/+102/
  +87）を正確に再現するが、実エンジン上の「liveMult を全属性に own 値へ置換する」変更は
  S2 では既存の off バフを外す方向に働き、頁の「S2 は無効」という記述は
  **頁の前提モデル上のみ正しい**。
- H4（バフ誤帰属）自体の機序仮説は D3 diff の `liveMultScope` 実装時に、現行エンジンが
  per-attr liveMult であることを踏まえて修正する必要がある（diff のまま適用すると
  H4-a の診断は頁の意図とずれる）。

## 5. H5-a の S2 L4 内訳と新規発見: S2/S3 トレースのフォト beat% 規則不整合

- 頁の H5-a は「b1 = 1000 + エール + フォト beat%（**max**）+ 25×su」と分解し、
  su を `su = (b1_mean − 1000 − エール − photoMax)/25` で逆算して乗算合成と比較している。
  この式は S2 L1/L2/L3/L5・S3 全レーンの頁値（+9.8/+8.6/+9.2/+7.7・0/0/+28/+12/0）を
  完全再現する（本検証 9.8/8.6/10.2/7.7・0/0/27.8/12.4/0）。
- ただし **S2 L4 については頁の分解が実データと食い違う**: トレースの b1 = 1506.6 は
  `1000 + 60(エール) + 175 + 206 + 25×2.63(su)` であり、逆算 su が 9.62 段になるのは
  「photoMax のみ（206）+ su 9.62」と解釈した場合。実際のスナップショット su は
  0 段×11 + 4 段×21 = 平均 2.63 段で、差分 175 = フォト1 の 17.5% が **sum で入って
  いる**ことを示す。
- 原因を git 履歴で確認: **commit 657d1ac（2026-09-05・サンプル3確定仕様の反映）で
  `sumScorePct(equipment, "beat_score")` → `maxScorePct(equipmentForScore, "beat_score")`
  に変更**されている。S2 トレース（d9c98c3・2026-09-03 収録）は旧 sum 実装、S3 トレース
  （657d1ac 収録）は現行 max 実装で生成されており、**pack_v3 の S2/S3 がフォト beat%
  規則の異なるコードベースで作られた不整合**が存在する。
- 含意: (a) S2 L4 の「+67.4‰ オフセット」は sum ベース sim に対する値であり、max ベース
  に直すと sim が 1506.6→1331.6 に下がるため implied は約 1067→1208 に**悪化**する
  （＝実機が S2 L4 で sum 的な b1 を使っている可能性が高い / または L4 固有の正ファクター
  がさらに大きい）。(b) H5-a の L4 +53 は「max 分解 + 逆算 su 9.62」という頁内部で整合
  するが実データと矛盾する内訳に基づくため、**H5-a の L4 予測は参考値**。
  (c) 次回 S2 関連の sim 再生成時は、現行 max 実装での再ダンプか、あるいは
  「sum/max どちらが実機仕様か」の判定実験（フォト 2 枚構成での遡及検証）が必要。
  S3 L4（b8 86.3K・pack_v2 §2.4）は max で整合済みなので、S3 の max は確定済み扱い。

## 7. その他の検証所見

- **S2 b50 の A+P 同時ポップは加算表示**: b50 L5 のポップ 858,900 ≒ A 828,900
  （gained − flat 補正後）+ P 30,000。A/SP と P が同一フレームで重なった場合、
  ポップは加算で表示される。E0 の「B1 内訳検証（A 単独ポップ想定）」には使えないが、
  rand 復元（§3.2 の 939–1041 区間）としては有効。
- S3 b2 L3 のポップ +123.3K は A（2,020,432）ではなく**同ビートで発火したフォト行
  （127,444）**の表示。A ノートと first フェーズ（photo）が同ビートで重なると、
  ポップは後発行で上書きされる可能性が高い。backfill の「A/SP ビートのポップ = A スコア」
  という帰属は、スキル行が A 単独のビートでのみ保証される。
- E1 の off 値グループは頁表が n≥3 のみ転記（本検証で n<3 の 3 グループを追加確認・整合）。
- §2.3 の来場数逆算は頁と ±0.1K の差（focus 加算の丸め方法の差）。fwd 列
  （スナップショットからの前向き計算）を併記済み。
