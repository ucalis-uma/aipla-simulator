## 0. 目的と台帳の定義

`deck.json` + `chart.json` 起点で sim を走らせ、ビートごとの「消費 / 回復 / 残スタミナ」を
実測 `measured_data.timeline[].stamina.current_stamina` と 1 ビート単位でつき合わせ、
乖離が **(H1) 初期値 / (H2) 1 回あたり倍率 / (H3) 台帳規則そのもの** のどれで説明するか決める作業。

スクリプトは 3 節を出す:

| 節 | 検査内容 | 位相問題耐性 |
|---|---|---|
| A | ビート系列の逐ビート比較（残高・Δ・消費計・回復計・発動内容）＋ 3 分類 | ✗（前後順ずれの影響を受ける） |
| B | **act 単位台帳**: 実測の「発動後に読まれた残りスタミナ」の同一 (lane,beat) 最小値 = ビート終了点として sim と直接較べる | ✓ |
| C | フォト 1 件コストの在庫突合（sim ストック vs 実測観測コスト） | ✓ |

補助スレッド（フォト同時発火）: 実測 act の (lane,beat) あたりフォト数の最大 = **1**、
sim も 1（`usedThisBeat` 予算で構造的に 1 まで）→ **記録された act の範囲では同時発火の証拠なし**。
ただし S3 の記録は 56 件しかなく（170 ビート × 5 レーンに対し約 3 割）否定材料にはならない。

## 4. C 節（フォト 1 件コストの在庫突合）— 訂正対象はここ

S3 のレーン別 stock（sim が持つフォトと `staminaCost`）と、実測で観測されたフォト 1 件コスト:

| 観測 | 実測コスト | sim stock | 判定 |
|---|---:|---|---|
| S3 L5 b1/b50 スコアUPスキルLv3 | 798 | `uph-uph-lane5-1` = 266 → **発動時 798** | **完全一致** |
| S3 L5 b2 獲得スキル-スタミナ多Lv2 | 1,620 | `uph-uph-lane5-3` = 540 → **発動時 1,620** | **完全一致** |
| S3 L5 b3 / b51 クリティカルスキルLv3 | **2,028 / 2,154** | 該当 stock 676 / 718 のいずれも固定値なし | **同一スキルなのに実測コストがビートで変わる（+6.2%）** |
| S3 L1 b1/b60 フォトViブーストスキルLv2 | 3,258 | `uph-uph-lane1-1` = 662 → 発動時 1,986 | sim 過小（実測の 61%） |
| S3 L3 b2 スコア獲得スキルLv1 | 3,030 | 該当 stock なし（L3 stock: 908 / 662 / 180） | 在庫マッピング誤り |
| S3 L3 b13 ViブーストスキルLv2 | 2,085 | 同上 | 同上 |
| **S1 L1 b1 PHOTOVoブーストスキル（伊吹渚 6/22）** | **662** | `uph-uph-l1-4` = 662 | **完全一致（1 倍）** |
| S2 L3 b1 PHOTOスコアUPスキルLv3 | 552 | `uph-uph-lane3-3` = 552 | 額一致（ただし sim は b1 で別フォト `photo-L3-2`=908 を発動） |

読み取れること:

1. **実測コストは常に stock 値の「3 倍の形」で現れる**（798 = 266×3 / 1,620 = 540×3 / 2,028 = 676×3 /
   3,030 = 1,010×3 / 2,085 = 695×3 / 3,258 = 1,086×3）。sim も発動時に ×3 しており**規則の向きは正しい**。
   S1 の 662 だけ 1 倍に見える → S1 のマイフォト stock はすでに 3 倍込みの値が記録されている（=二重換算は起きていない）。
2. **同じスキル名・同じ Lvなのに実測コストがビート間で変わる**（2,028 ↔ 2,154）。
   → 実ゲームのフォト消費は固定値ではなく**何かに比例して揺れる**。sim は固定値。ここが残余不一致の本命。
3. **sim が発動するフォトの取り違え**（S2 L3 b1 で `photo-L3-2`=908 を発動、実測は 552 のスコアUP）。
   消費額が違うフォトに差し替わると、額だけでなく buff の内容もズレる（スコア側にも響く）。
4. 不一致セルの P / A コストが一致している事実と整合: **台帳の欠陥は「フォト 1 件コストの決まり方」と
   「どのフォトを発動か」に局在**する。

## 5. 結論（プロンプトの 3 分類への回答）

| 候補 | 判定 | 根拠 |
|---|---|---|
| H1 初期値 | **棄却** | 初期値は 25/25 レーンで sim = 実測（S1 L1 の 8,900 は誤読、max 9,092 が一致） |
| H2 1 回あたり倍率 | **棄却** | S1 L1 が 176/176 完全一致、S4 L5 が 57/170 一致。同一サンプル内でレーンにより一致度がバラバラ。P/A の 1 件コストは全サンプル一致 |
| H3 台帳規則そのもの | **一部成立（＝訂正対象はこれ）** | 局所はフォト：①同一スキルの実測コストがビート間で ±6% 動く ②sim のフォト取り違え ③一部 stock の額不一致（662 vs 1,086 等） |
| （位相）ビート内の前後順・読取時点 | **A 節の乖離の主因** | timeline の current_stamina は発動途中の値（S3 L1 b1: 9,411 vs 終了点 7,425）。終了点同士では消費計 3,258 が完全一致 |
| H4 フォト同時発火 | **本データでは検証不能** | act 記録の範囲では 1 ビート 1 レーンのフォト発動が 2 件以上のセルなし（max 1）。ただし記録が約 3 割しかなく否定もできない |
| 回復規則（15/段階/特徴） | **本データでは検証不能** | 回復の正体がビート跨ぎで分散している（S2 L1 で b41/b42 に 4,626/2,057 等、1 件では説明不能な塊）。act Σ と recovery の対応が 1 件ずつ取れない。act 単位検査（B 節）が通るサンプルでしか確定できない |

**engine.ts は変更していない。** 現時点で入れるべき訂正は「定数」ではなく、
(a) フォト 1 件コストの決まり方（比例要因の同定）と (b) 発動フォトの選択、という 2 つの**規則の再定義**で、
どちらも T4/T5 golden の発動結果を動かすため、材料がそろうまで保留が正しい。
