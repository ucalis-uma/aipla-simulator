## 1. スタミナ再読取(最重要) — 完全解決

### 1.1 失敗の原因(旧パイプライン)

スタミナ表示は `現在値/最大値` の白字だが、**該当区間では表示の背景に黄色ハイライト帯(RGB≈221,221,77, グレイ値≈205)が敷かれる**。旧 `number_ocr` は閾値 180 で二値化するため、白字(255)と黄帯(205)が**一体化した巨大コンポーネント**になり、数字が抽出できなかった(空文字→null)。
一部のビートでは帯の縁のアンチエイリアス部分だけが小コンポーネントとして分離し、`911` / `0911` / `60911` といった**断片誤読**を生成した。これが Lane 2 の `60,911`(max超過) および旧データの `911` (max以下だったため異常検知をすり抜けた) の正体。

### 1.2 正しい読取方法(確立)

- クロップ: `y 495–545, x 690–940` (現在値 x≈721–812, スラッシュ x≈816, 最大値 x≈830–923)
- 二値化閾値: **235** (黄帯≈205 と白字 255 を分離)。全 785 セルでこの閾値のみで読取成功
- 検証: スラッシュ右の最大値部がレーン既知 max (L1=20066 / L2=15609 / L3=18730 / L4=16033 / L5=16332) と**完全一致した場合のみ採用**(自己検証型 OCR)。785/785 セルで max 検証合格、1桁あたり最低照合スコア 0.70 以上

### 1.3 検証結果

| 検証 | 結果 |
|---|---|
| 785 セル再読取 | **785/785 成功** (max部検証込み) |
| 既存の「正常」とされた 568 セル | **全件 1 の位まで完全一致** (手法の一貫性証明) |
| 修正対象 217 セル | L1 56 + L2 55 + L4 106 = **217** |
| 発動ログ `skill_activations[].stamina` との照合 | 照合可能な全ビートで一致 (下表) |

アンカー照合 (新読取値 = 発動ログ表示値):

- L1: b101=14036, b136=13942, b150=13775, b151=12380
- L2: b47=11147, b48=10637, b50=10480, b52=9970, b60=8893, b86=8853, b93=8683, b97=8090, b100=7933, b115=7311, b120=6234, b138=5724, b144=5603, b147=5010, b150=4853, b152=4343

### 1.4 主な発見

1. **Lane 2 の誤値は b97–101 だけではなかった**: b60–96 の `911` も全部誤読。真値は b60–85=8893, b86–92=8853, b93–96=8683 で、こちらは max 以下だったため 05 の全件検査をすり抜けていた。**修正は b47–101 の 55 セルに及ぶ**。
2. **スタミナは beat 経過ではほぼ減らず、スキル発動(消費/回復)でのみ変化する**。新旧マージ後の全レーン系列がこれと整合する(例: L1 b101–135 は 14036 で不変, b136 の A 発動で 13942)。スキル消費値(検証データ: 187/202/279/458 等)との直接の差分計算は発動シーンのフレーム位相分ずれがあり 1 の位では説明できないが、**表示値同士の突合は全点一致**しているため、ゴールデン照合は「表示値」で行うのが正。
3. 解決不能セル: **0**。

### 1.5 残る不確実性

なし(全セルが max 検証+アンカー+近接ビート連続性の三重整合を満たす)。強いて挙げれば、発動 cutscene 内の表示値とレーン画面の表示値の**取得タイミング差**(同 beat 内の前後)により、スキル消費量の差分検算は ±数百スタミナの粒度でしか行えない。これは仕様確認の範囲外で、表示値照合には影響しない。

## 2. CT 表示 (skill_cts) 再アプローチ — 読取方法確立+モデル復元

### 2.1 旧データが 0/1/6 しか持たなかった原因

- クロップ `img[1790:1870, base_x:base_x+260]` は**数字の上端しか取れていなかった**。CT 数字は実際には **y 1855–1886** (高さ≈31px) に描かれる
- ready 状態のアイコンには **Lv バッジ(x≈スロット左端, w8 h22 の '6' 等)とアイコン白部**が閾値 220 で digit と誤認識された → '0','1','6' のみが乱れて記録されていた
- レーン毎に録画のオフセットが異なり(L5 のバーは他レーン比 +28px 右, L4 は slot2/3 で ±10–30px ずれ)、固定スロット枠では隣スロットの桁を混入していた

### 2.2 正しい読取方法(確立)

- 領域: `y 1838–1898`、スロット枠はレーン別に較正 (例: L1 slot1=[24,74], slot2=[86,136] / L5 slot3=[175,225]、単位はレーンストリップ内 x)
- 閾値 **230**: CT 中のアイコンは暗転オーバーレイが敷かれ、白字(≈255)のみ抜ける。ready 状態ではバッジ/アイコン白部が (h≥33 または面積不定で) 混入するため、**デジット高さ h≈31 (22–32) でフィルタ**
- グリフは ASCII 展開により目視同定済み ('49'@L1b2, '48'@L2b116, '50'@L2b115, '30'@L1b47, '28'@L1b48, '10'@L1b40, '01'@L1b49, '12'@L2b152, '10'@L2b154, '9'@L2b155, '8'@L2b156, '24'@L1b99 など 20 点以上)

### 2.3 CT 表示の仕様(実測で確定したルール)

1. **発動フレームで CT 満値を表示** (例: L1 slot2 = P かんしょ〜かい CT50: b1='50', b50='50')
2. **以後 1beat につき -1**。表示値 = `CT - (b - act) ± 1` (±1 は動画フレーム位相とカウント瞬間のずれ。桁がパルスアニメーションするためフレームにより桁サイズが変動する)
3. **常に2桁(leading zero)表示** ('01','09' 実測)
4. **0 到達 (b = 発動+CT) で表示消滅** = 再使用可能。→ **発動間隔は CT-1 以上**(CT50 なら gap≥49)。これは 82 発動すべての間隔と矛盾なく整合し、05 の「gap ≥ CT」を CT-1 へ精化する
5. 実測系列の例 (L1 slot2, act=b1): `b1:'50', b2:'49', b4:'46', b5:'45', b6:'44', b10:'40', b40:'10', b48:'02', b49:'01', b50:'50'(再発動)` — 中間に ±1 の読取揺らぎがあるが、傾きは厳密に -1/beat

### 2.4 発動ログから決定的に復元した CT 表示テーブル

13 スロット × 157 beat の表示値テーブルを `research/fixes/stamina_ct_fixes.json` の `ct_fixes.display_table` に出力した(モデル値。スキル↔スロット対応は発動ログの reset が CT 満値と一致することで全て検証済み)。

構造検証: 「表示桁数がモデル値の桁数と一致」の判定で **1997/2041 (97.8%) 合致**。残り 44 は (a) スコアポップアップ等の**白色オーバーラップによる桁隠蔽** (L2 slot2 b128–134, L4 slot2 b148–154 等 — 大コンポーネントの重なりとして確認済み)、(b) 帧位相ジッターによる ±1、に全て分類でき、**モデルと矛盾する読みは 0 件**。

### 2.5 CT 変調イベントの実測

| イベント | 内容 | 実測根拠 |
|---|---|---|
| **CT短縮 (b106)** | L4 A ドリームウエディング「隣接するアイドルのCTを減少」→ L3・L5 の表示残CTが **約15** 減少 | L3 P逆襲: 発動間隔 50→35 (b101→b136, 短縮がなければ b150 まで不可)。L5 Pさらけ出す: b60→b106 (gap 46, 通常 59 必要) で即再発動。両者を同時に満たす減少量は 15 (14–15 の幅で frame 位相依存) |
| CT増加 | L3 A 星見プロ「同じレーンの相手のCT増加」(b2/b69/b156) | 表示上のジャンプは観測されず。対象スキルが READY 中だったか、最終 beat のため表示変化が取れないと判断(値を断定しない) |

### 2.6 結論

旧 `skill_cts` は**使用不可確定**(全セル無効)。置き換えとしては `ct_fixes.display_table` のモデル値を用い、テスト時は「発動 beat で CT 満値」「以後 -1/beat」「gap ≥ CT-1」の 3 則をアサートする。個別 beat の OCR 値を 1 の位でアサートするのは(±1 ジッターのため)非推奨。

## 3. Lane 3 stat_value の平台上限 — 表示上限と判定

再 OCR (x 410–650, 閾値 180/200, conf ≥ 0.84) による Lane3 ボーカル値の推移:

| beat | 表示値 | 倍率 (÷626,223) |
|---|---|---|
| 38–49 | 1,722,113 | ×2.75 |
| 50 | 1,863,013 | ×2.975 |
| 51–59 | 2,082,191 | ×3.325 |
| 60–67 | 2,301,369 | ×3.6743 |
| **68–156** | **2,348,336** | **×3.75 (固定)** |

判定: **b68 以降の 2,348,336 は表示上限** (= floor(626,223 × 3.75) = ボーカル上昇合計 +275%)

根拠:

1. b68 以降 b156 まで 30 サンプル全て 1 の位まで完全固定。この間に b101 の強化効果増強(→千紗)等、段階数を増やす効果が発動しているが表示は無反応
2. b68 までの推移は加算ステップで精緻に説明できる: +140,900 = floor(626,223×0.225), +219,178 = floor(626,223×0.35) ×2回。ところが次のステップを同じ規則で足すと 2,301,369 + 46,966 = 2,348,335 となり、**実表示 2,348,336 は「floor(626,223 × 3.75)」と 1 の位まで一致**する。つまり最後のステップは加算則を外れて「×3.75 の上限値への一致」で描画されている
3. ×3.75 (+275%) という端数のない上限値そのものが上限解放仕様(ボーカル上昇の上昇上限)を示唆

含意: **b68–156 の Lane3 stat_value を実値として計算機の照合に使ってはならない**。b68 以前の 4 変化点 (1722113/1863013/2082191/2301369) は実表示として信頼できる。真の内部値は上限を超えて継続上昇している可能性があり観測不能。
