# 06. テスト計画（計算コア単体テスト〜ゴールデンテスト〜CI）

- 役割: テスト・ゲーム実測値との照合方法検討担当
- 前提資料: `research/05_data_quality.md`（信頼性マップ・不変条件 I-01〜I-16・異常値リスト）
- 原則: **実測データの信頼度に応じてアサーションの強度を変える**こと（◎=完全一致、○=条件付き完全一致、△=レンジ/近似、✕=アサート禁止）。信頼度を超えるアサーションは偽失敗を生む。

---

## 1. 目的と範囲

| 区分 | 内容 | テスト方針 |
|---|---|---|
| 段階A 単発スコア計算 | 1 ビート/1 スキルのスコア式 | 単体テスト＋手算値との完全一致 |
| 段階B タイムラインシミュレータ | ライブ全体のイベント駆動処理 | ゴールデンテスト（measured_data.json）主体 |
| 段階C データ統合型 | カード/譜面 DB から編成構築 | 編成→beat 0 ステータス照合（I-09）＋B の全テスト |

MVP は段階 B（編成入力は手入力/JSON インポート）を想定。段階 C のカードマスタは未整備のため、テストも B までを確度 Confirmed の対象とする。

---

## 2. テスト対象アーキテクチャへの前提要求（アーキ担当との合意事項）

テスト可能性のため、計算コアに以下を要求する。

1. **純粋関数中心**: 入力（編成・譜面・発動ログ・乱数列）→ 出力（状態列・スコア列）が純粋。グローバル状態・実時刻・UI に非依存。
2. **乱数の注入点**: `Rng` インターフェース（`nextCritical()`, `nextScoreRoll()` 等）を明示し、`FixedRng(seed)` / `MinRng` / `MaxRng` / `ReplayRng(実測値列)` を差し替え可能に。
3. **整数演算の明示**: 丸め位置（floor/round と適用順）を計算式のパラメータとして注入可能にし、丸め差分をテストで特定できるように。
4. **イベント列の可観測性**: シミュレータがビートごとの内部状態（スタミナ・バフ multiset・CT・コンボ）を途中出力できること（ゴールデン照合の対象）。

## 3. テストピラミッドと Phase 計画

```
T0 データ健全性（I-01〜I-16）           ── 実装前に実行可能
T1 単体: ステータス式・スコア式・丸め    ── 手算＋実測アンカー
T2 コンポーネント: バフ/CT/コンボ機構   ── 合成ケース
T3 ゴールデン: beat 0 編成照合          ── I-09
T4 ゴールデン: 開幕バースト beat 0〜10   ── 発動順・効果時間
T5 ゴールデン: 全タイムライン照合        ── リプレイ/統計モード
T6 回帰: 実測データ＋将来の第2実測       ── CI 常時
```

| Phase | 内容 | 入力 | 合否基準 |
|---|---|---|---|
| T0 | measured_data.json 自体の健全性検査 | measured_data.json | I-01〜I-16 全 passer（既知異常は除外リストで明示） |
| T1 | 単体（§5 カタログ） | 手算ケース | 全件完全一致 |
| T2 | 機構単体（バフ積算・上限・CT・コンボ・発動順） | 合成ケース | 全件完全一致 |
| T3 | **beat 0 の 5 レーン補正後ステータス再現** | verification_data（基礎値・スタッフ・エール・交流Lv） | 5 レーン × 4 ステータス 1 の位完全一致（L1 Vo 334,153 / L2 Vo 401,055 / L3 Vo 626,223 / L4 Da 284,769 / L5 Vo 339,715、Stamina 各 max） |
| T4 | beat 1〜10: 開幕 9 連発動の処理順・効果付与・初手スコア | 発動ログ order 1〜11 | 発動順・対象・効果 multiset（L1/2/4/5 完全一致、L3 部分一致）・stamina 完全一致。beat 1 のスコアは 0 扱い（既知の帰属不確実性）を許容 |
| T5 | 全 156 ビート | 全ログ | §4 の 3 モード基準 |
| T6 | 回帰 | 同上 | T5 を CI で常時実行 |

**段階的検証（実装フェーズでの「1 レーンずつ・1 スキルずつ」）**:
- T4 の前に「Lane 3 のみスコアを積算し、他レーンは 0 固定」→ beat 2〜10 の Lane 3 ポップ（有効数字内で ±0.1K〜0.1M のレンジ照合）。
- 続けて Lane 5（スコア獲得フォトのみの単純ケース）→ Lane 1/2/4（サポータ）→ 最後に全レーン合算。
- 1 スキルずつ: 発動ログから 1 件だけ有効化した縮小譜面を生成し、効果時間の開始/終了ビートを effects 推移で確認（§5-OB1）。

### 4.2 乱数の扱い（3 モード設計）

実測 §3-L の通り、同一状態のビートスコアが ±4% 揺れるため、**生の RNG 再現なしに最終スコア 17,529,132,014 の完全一致は原理的に不可能**。そこで:

- **Mode R（リプレイ）**: `ReplayRng` に実測のビート別獲得スコア列（= 実現した乱数結果）を注入し、非乱数ロジック（スタミナ・バフ・CT・コンボ・発動順・効果時間）を **cumulative 完全一致**で検証する。乱数以外のバグを全て捕捉できる主力モード。
  - 注入粒度: ビート合計（帰属は ±1 不確実のため）。レーン配分はポップアップ近似につきレンジ照合。
- **Mode D（確定モード）**: MinRng（全 MISS 判定相当/乱数下限）/ MaxRng（全クリティカル・乱数上限）/ 期待値モードで、`min ≤ 実測 ≤ max` と `expected ≈ 実測（±k·σ）` を検証。
- **Mode S（統計）**: 固定 seed 100 本のモンテカルロで合計スコア分布を作り、実測値が中央 90% 区間に入ること。seed を変えても分布が不変なこと（シード依存バグ検出）。

固定 seed テスト: `FixedRng(seed=1)` で同一入力 → バイト等しい出力（決定論テスト）。プラットフォーム差（Math.floor 等）が出ないよう演算は整数系に統一。

### 4.3 クリティカル 22.3% / HIT 94.4% からの逆算検証観点

- 逆算の実測制約（05 §3-H）: N=155〜157 のいずれでも両率が同時に整数カウントにならない → **クリティカル枚数は 33〜35、HIT は 146〜148 のレンジ制約**としてのみ使う。
- 検証観点:
  1. Mode S のモンテカルロで、シミュレータのクリティカル率実装（baseCri + スタッフ +2,705 + エール +600 + クリティカル率上昇バフ等）から得られる期待クリティカル率が 20.8%〜22.9%（33〜35/155±丸め幅）に収まること。
  2. クリティカル有無によるスコア差 = クリティカルスコア補正 +25.5%（エール）× クリティカル係数バフ段階 の単体テスト（§5-CR1）。
  3. HIT 94.4% 前後 ↔ MISS 0 ↔ コンボ 155 の整合（MISS>0 の合成ケースはコンボ切断テストで別途担保）。
  4. 判定内訳は低信頼のため、**式確定の root of truth には使わない**。将来の第 2 実測（判定画像連撮）でビート単位クリティカルフラグが取れれば Mode R へ組み可能。

### 4.4 実装していない効果の扱い

- 未実装効果の除外リスト（`golden_exclusions.json`: 効果 id / 理由 / 影響レーン・ビート）をコードと分離管理し、「除外ありモード」の期待値は除外後の実測再計算ではなく **除外なし完全一致を目標に、逸脱時に diff レポートで差分ビートを列挙**する設計とする。
- 推定式（Estimate）を使う箇所は、テストに `accuracy: Confirmed | Strong estimate | Estimate | Unknown` タグを付け、Estimate 以下は警告 + 記録のみ（fail にしない）→ 式の確度表示（prompt_plan 要件）へフィードバック。

## 6. テストデータ管理と実測データとの紐付け

1. **fixtures 構成**
   ```
   tests/fixtures/
     measured_data.json      → 原本のコピー（改変禁止・SHA-256 を記録）
     verification_data.json
     known_anomalies.json    → 既知異常の除外リスト（beat/lane/field/理由）
     golden_expectations.json→ T3/T4 用の事前計算アンカー（生成スクリプトで自動生成）
     synthesized/            → 合成ケース（MISS・スタミナ 0 等、実測にない境界）
   ```
2. **紐付け規約**: 各テストの失敗メッセージに `(beat, lane, field, expected, actual, 根拠画像ファイル)` を出す。発動ログには `file: IMG_####.PNG` が付くため、失敗時の目視再検証が 1 クリックで可能。
3. **除外の明示義務**: known_anomalies を使った pass は `-v` で常に一覧表示（黙示の skip を禁止）。理由コード: `OCR_STAMINA` / `OCR_CT` / `MERGE_DUPLICATE` / `FRAME_TIMING` / `UNREADABLE`。
4. **第 2 実測の追加**: `fixtures/lives/<id>/` に同一スキーマで追加でき、全ゴールデンがデータ駆動で拡張される設計（ハードコード禁止）。

## 7. CI（Windows 上）での実行方法案

| 項目 | 案 |
|---|---|
| ローカル実行 | ワンコマンド `run_tests.ps1`（T0→T6 順実行、失敗時に diff レポート出力）。push 前の手動検証用 |
| CI サービス | GitHub Actions `windows-latest`（作業環境と同一 OS）。プッシュ/PR 時に T0+T1+T2 を必須、T5 ゴールデンは別ジョブ（実行時間 < 1 分見込み） |
| エンコーディング対策 | **実測プロジェクトでの教訓**: PowerShell 5.1 は UTF-8 BOM なしの .ps1 で日本語を破壊する。テストスクリプトは (a) UTF-8 BOM 付き保存、または (b) PowerShell 7 (`pwsh`) / Python / Node で実行。`.gitattributes` で `*.ps1 text working-tree-encoding=UTF-8` 等を明示 |
| 日本語パス対策 | 作業ディレクトリが `アイプラ`（非 ASCII）。テストランナは `Path` API 経由のみで扱い、8.3 名や ANSI 変換に依存しないこと。CI ではリポジトリ checkout 先を ASCII パスにする（例: `D:\a\ipcalc\`） |
| 冪等性 | golden JSON はリポジトリ同梱（ネットワーク・ゲーム端末不要）。データ更新時は SHA-256 再計算をコミット要件に |
| レポート | JUnit XML 出力（Actions の test reporting で可視化）+ 独自 diff レポート（ビート×レーン差分表を HTML/markdown で artifacts 添付） |

| 候補 | 長所 | 短所 | ゴールデン適合度 |
|---|---|---|---|
| TypeScript + Vitest/Jest | JSON 扱いが容易、snapshot/expect.closeTo、並列高速。ローカル Web/Tauri 構成と同言語化 | 数値の bigint 扱いに型注意（17.5 兆は number で安全: 2^53 未満） | ◎ データ駆動 parametrize が容易 |
| Python + pytest | parametrize/fixture が強力。**既存 OCR パイプライン（scratch/）が Python** でデータ再生成と同一言語 | アプリ配布（Windows ローカル起動）ではランタイム同梱が必要 | ◎ テスト専用にしてもよい |
| C# + xUnit | 型安全・Windows ネイティブ配布と親和。decimal/long で精密 | セットアップ記述がやや冗長 | ○ |
| PowerShell + Pester | 追加ランタイム不要・Windows 素の状態で動く | 数値式・JSON 深入れの記述性が低い。エンコーディング地雷（§7） | △ T0 の健全性チェック限定なら可 |

推奨方針: **アプリ本体の言語に追従しつつ、T0（データ健全性）だけは言語非依存で最優先整備**（Python or PowerShell で即日化可能）。ゴールデンランナーは「JSON 入力 → 結果 JSON → 比較器」というデータ駆動形式にし、言語決定（アーキ担当）後に薄く移植できるようにする。数値はすべて 64bit 整数（最終 17,529,132,014 < 2^53 = 9.0×10^15 だが積算途中で浮動小数を使わない方針を明記）。
