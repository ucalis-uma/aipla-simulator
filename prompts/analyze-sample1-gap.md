## 3. 分析手順

### 3-1. ビート単位の乖離マップを作る（最初の 1 ステップ）

1. CLI で確定値タイムラインを取得:
   `npx tsx src/cli/simulate.ts --input examples/nested-sample.json --n 0 --crit-rate 0 --out research/17_sample1_gap_analysis/confirmed.json`
2. 診断スクリプトで `simulateTimeline` を直接呼び、**完全な LaneScoreEventTrace**
   （basicScore / skillPowerPermil / b1Permil / comboFactorPermil / fanFactorPermil /
   critFactorPermil / isRatioScore・buffSnapshots・activations）を JSON 化する。
   CLI 出力の events は簡略版（lane/kind/gained/crit）なので factor が取れない点に注意。
   SimSourceData の構築は `src/cli/simulate.ts` の `loadSourceData` をスクリプトへ複製してよい
3. 実測 `measured_data_v2.json` の timeline と並べ、**ビート毎・レーン毎の gained 差分表**を作る:
   - 乖離が**初めて生じるビート**とその直前の発動
   - 乖離率が一定（全体スケール差）か、特定ビートで跳ぶ（イベント差）かを判定
4. レーン別内訳を実測（§1-2）と比較 — 乖離が L3 に集中するか、全レーン均一か

### 3-2. 乖離要因の切り分け（証拠を残しながら）

仮説ごとに「実測値との突合」で検証し、**寄与率を見積もる**こと:

1. **発動スケジュール・バフ段数**: 実測 effects[{name, stage}] と シミュ buffSnapshots を
   ビート毎に照合。**最初に段数がズレるビート** = 犯人のスキル（持続・対象・段数・増強量の
   いずれかが違う）→ 該当スキルの decodeSkillLevel 復元値と skill_order のバナーテキストを
   1 行ずつ突合（%値/段数/[Nビート]/対象/条件）
2. **マスタ解析値の検証**（最有力仮説）: サンプル1 の 15 スキル全てについて
   `skills_levels.json` の該当 Lv 行（p/st/d/v）をゲーム内テキストと照合。
   特に大スコア A/SP（夏を先取り 360%、新たな衣装と新たな決意、それが勇気になるから）。
   importer（build_data_phase6.mjs）の該当 efficacyType の写像規則も確認
3. **大スコアビートの検算**: b51 / b143 / b170 / b176 を T5 方式（1 の位検算）で:
   実測ビートスコア = Σレーン（basicScore × SkillPower × B1 × combo × fan × crit）が
   成立するか。成立しないなら、どの因子がいくら違うかを逆算
   （例: 実測/シミュ比 = 0.6 が SkillPower 0.6 で説明できるか、等）
4. **全体スケール仮説**: fanFactorPermil（audience 71000 由来）・stageFactor を変えて
   確定値がどう動くかを config で試す（`fanFactorPermil` 直指定可）。
   乖離が全域ほぼ一定率ならスケール系、特定イベントで跳ぶならスキル系
5. **type36 scaling（集目段階数参照・最有力候補の一つ）**: サンプル1 の大スコア SP
   それが勇気になるから（sk-ai-05-fest-00-1）は `sn=1`（スケーリング未適用マーカー）で
   b143 +51.5M を**過小評価しているはず**。乖離方向の説明候補。
   裏取り済みアンカーあり: Peing 質問箱 id=1187772111「愛の集目依存部分のSPパワー
   （集目10時**1921%**）」= Lv6 基礎 1130% × (1 + 0.07×10) に完全一致 → **+7%/段**
   （research/16 §3 参照）。サンプル1 の b143 時点の実測集目段数で
   「1130%×(1+0.07×段数)」（デッキ Lv4 は基礎 880%）の検算式で
   実測 +51,566,931 が成立するかを 1 の位検算し、確定させること。
   ただし**乖離方向と逆**（シミュ過小）なので、1.67 倍の過大乖離の主因にはなれない。
   b51（新たな衣装と新たな決意・scale なし 360-440%）と合算で辻褄が合うかも確認
   【プレフライト済み 2026-09-01・`research/17_sample1_gap_analysis/b143_check.ts` の結果メモ参照】:
   シミュ b143 = score_get 行 39,883,175（basic 456,442 × **power 10000‰** × b1 1.677 ×
   combo 3.120 × fan 1.670）+ ratio 行 19,589,380 = 59,472,555（crit なし）。
   実測 51,566,931（crit 込み・ポップ=critical）。つまり **scaling を適用しなくても
   シミュは実測の約1.5倍**。さらに注目点:
   - シミュ power=10000‰（Lv5 の 1000%）→ **deck.json の skill_levels は 3:Lv4（880%）のはず**。
     Lv 行の反映が効いていない（golden がマスタを上書き？）可能性 → 3-2-2 で確認
   - シミュ L3 snapshot csu=14 / vocal_boost=12 に対し実測表示は csu=9 / boost=9
     （実測は「表示は段数を下限クリップしている」説と「シミュが過剰付与」説がある。
     csu/boost の付与元を 1 ビートずつ突合すれば判別できる）
   - basic 456,442 は deck stat × 重み × λ の実測 stat_value 402,390 ベースとの突合も可
6. **コンボ帯**: 実測 COMBO は最大 120（リセットあり）。シミュの CB テーブル（100+ → +50%）
   がこの帯域で正しいかは T5（リセットなし・別帯域）では検証されていない点に注意
7. **ポップなし 87 セル**: 実測でスコアポップの無いレーン×ビート。チャート上
   ノートが無いのか（→ シミュが過大計算）表示だけの問題なのかを分類し、
   その 87 ビート分のスコア合計が乖離の何%を説明するか見積もる

### 3-3. 副主題（データからまだ掘れる未解明事項）

   94.1% になる分母の候補を全探索（T5 の値と共立する候補を優先）
2. **RANK S+67 の内訳式**: スコア/目標比からの導出式を T5 の RANK 値と共に当たり
   （research の T5 リザルト記録を参照）
3. **b130 の L3 csu 16段**（b129=10 → b130=16 → b131=6）: measured_data_v2 の
   effects 並びから合算・更新順序の整合性を検証
