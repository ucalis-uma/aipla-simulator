## 2. 最大の論点: lane3 の IMG↔beat 対応（ユーザー提供知見）

lane3 だけ 432 枚と他の 2.75 倍ある。ユーザー（2026-09-05）によると:

> 各ビートの写真枚数は「現在の効果ウィンドウに付与されている状態の個数」で決まる。
> 効果ウィンドウは一度に 6 個まで表示。状態が 0〜6 個ならそのビートは 1 枚、7〜12 個なら 2 枚、
> 13〜18 個なら 3 枚。番号は若い順。付与状態の個数は下段の各アイドルの青い丸の個数に対応し、
> 11 個以上は +K のような表示になる。

つまり **lane3 はビートあたり 1〜3 枚のバースト**で、`IMG_(637+2N)` という単純式は成立しない
（検証済み: research/09_buffs_criticals.md には b1=IMG_0639/0640・b2=IMG_0641/0642・
b3=IMG_0644・b6=IMG_0649/0650・b8=IMG_0654・b20=IMG_0677/0678・b52=IMG_0756 の実績対応がある。
これをシードに照合しながら全対応表を作る）。

### 手順（lane3 対応表の構築）

1. **自動推定**: 各 IMG の「下段の青い丸の個数」（または効果ウィンドウの段数合計）を PIL で
   特徴抽出し、ビートあたりの予想枚数（1+floor(dots/7)・dots≥11 は表示注意）を計算 →
   累積で beat 候補を割り当てる。research/09 の既知対応（上記シード）と矛盾しないか検証
2. **目視検収**: 候補対応表のうち、既存 `gained_score_displayed` があるビート（674 セル分 =
   ポップが画面に出ているはずのビート）で、割り当てた IMG にそのポップが写っているかを
   サンプル目視（または `tools/backfill/make_pop_sheets.py` のクロップ設計を流用）で確認
3. **NNNN 連続性の確認**: lane3 の IMG 番号に欠番がないか `ls` + 番号 diff で確認。
   欠番があればどこかの書類（research/14_visual_verified_golden_data.md や
   `スコア分析サンプル/verification_data*.md`・measured_data_summary.md）に記載がないか探す。
   なければ「欠番あり・対応不能区間」として null + 理由で記録（捏造禁止）
4. **lane1/2/4/5 は単純対応の可能性が高い**（157 枚 = 157 ビート）が、lane1 先頭 IMG_0323 が
   beat 0 かは確認が必要（b0 のポップは null 既存なので、アイドル名帯・BEAT 表示・コンボ数字
   （既存 timeline の combo 列）との照合で決める）
