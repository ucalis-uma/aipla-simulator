## 1. 出発点（確定済みの事実・数値）

- アクション5 の全ビート×全レーン・マッピングで「**sim=0 かつ実測 pop>0**」は
  **S3 = b4 L2 2,300,000 / b34 L2 2,900,000 / b169 L3 2,500,000**、**S2 = b112 L5 1,000,000 / b148 L4 3,200,000**、**S1 = 0 件**。
  全て A ノート（`charts_all.json` の type=2）で、発動トレースは `A/L#:FAIL(stamina_short)`（同ビートの P/フォトも同時失念）。
- 失点の金額: **S3 = 11 件 7,700,000（実測の 9.7%）/ S2 = 2 件 4,200,000（5.4%）**。
  **S3 の −5,585,360（−7.03%）は失点 7.70M で過不足なく説明できる**（失点を除くと逆に +2.1M の過剰側）。
- **規則変更の要否を判定する予備証拠（重要）**: 同サンプルの**発動成功**セルの実測 pop は
  S3 = b24 L3 2.10M / b79 L3 2.00M / b123 L3 2.00M / b42 L4 3.20M、S2 = b142 L3 3.90M / b41 L3 3.10M / b126 L1 2.00M。
  → **失点疑いの pop（1.0〜3.2M）は成功発動と同じ規模**。
  よって「ヒット時に小さく払う（発動と独立）」よりも **「実機では発動していた＝sim のスタミナ帳簿が過少」**が最有力【Estimate】。
  例: b169 の実測 stamina_bar L3 = 541 に対し sim 333（= sim だけコストを割れる／実機は割れない）。末尾だけでなく全ビートで比較すること。
- H3（A ビートにもビートノートが実在する＝譜面モデル誤り）は**ほぼ否定済み**: 失点ビートの隣 sim 計は 19〜27 万
  （例 b33=265,530 / b35=254,417）で、実測 pop 230〜290 万を説明できない。
- `settleSkillNote` を「ヒット基本点＋発動成功時に上乗せ」へ分離する規則変更は **フォールバック**（タスク3 のゲートで H2 が否決された場合のみ、かつユーザー承認後に着手）。

## 3. タスク

### タスク1 全ビート×全レーンのスタミナ系列突合（読み取り専用）
sim の帳簿と実測 `stamina_bar` をビート別に並べ、**初回分岐ビート**（|sim−実測| ≥ max(200, 実測最大値の 5%)）をレーン別に特定。
対照として **S1（末尾一致 ±19）** を必ず入れる。出力 `phase16_action6_stamina_audit.ts` + `_out.txt`:
レーンごとに {初期値, 分岐ビート, 分岐直前までの消費内訳（skill_id / 段数 / 1 回コスト / 回復）} を printed すること。
### タスク2 分岐要因の同定
**過大消費 / 過小回復 / 初期値不足**のいずれかを特定する（`deck.json` のステータス、`yale_bonus`、スタミナ上昇スキル、CT）。
読めない値は捏造せず `null` + 【Estimate】/【Unknown】。ゲーム内データはスクショではなくマスタ参照（`research/03_data_sources.md`）。
### タスク3 発動失敗 5 セルの再現（**裁定ゲート**）
タスク2 の訂正を仮適用（engine 修正前に「初期値/コストの上書きオプション」を一時引数で入れて可）し、
**b4 L2 / b34 L2 / b169 L3 / b112 L5 / b148 L4** が ①発動成功になり ②sim のビート×レーン獲得が実測 pop の **±15% 以内** なら **H2 確定**。
届かない場合は H1（ヒット時払い）に切替の是非を報告書で比較し、** engine を規則変更する前にユーザー承認を仰ぐ**（= 分岐 (b)）。
