## やさしい解説（ここだけで概要が分かる版）

A11 で「S2 が −3.65% 足りない」原因を追い込んだところ、**beat ノート（ふつうのノーツ）の素点だけが、
レーンごとに一定の倍率でずれている**ところまでは分かった。ところが、その倍率を
「デッキの 3 属性（ボーカル／ダンス／ビジュアル）の重みのせい」とすると、**どの重みでも実測に合わない**
（最小でも誤差 2.3%、ふつうのノイズは 0.5%）。つまり原因は重みの数値ではなく、
**式の形か、デッキ 3 属性以外の何か**である。

その「何か」を特定するには、**同じデッキを別のレーンに置いた実測**が必要（いまは
「デッキの中身」と「どのレーンか」が完全にセットで動いていて区別できない）。

さらに A11 の作業中に、**もっと手前の重大な矛盾**が見つかった:
**2 つの公式ハーネスが同じサンプルで違うスコアを出す**。

| 口径 | 使うツール | S1 | S2 | S3 |
|---|---|---:|---:|---:|
| legacy（`audience` のみ） | `tools/analyze_beat_score_models.ts` | 116,829,040 | 74,895,810 | 78,485,270 |
| lanefans（`laneFans`+満員ガード） | `tools/audit_hidden_cells_sim.ts`（**既定**・A10 監査が使う） | **114,162,150** | 74,669,710 | **77,425,702** |
| （実測） | — | 116,537,513 | 77,732,383 | 79,411,389 |

S1 と S3 は**満員**（laneFans 合計 = 会場キャパ）なので、満員ガード（`src/formula/fan.ts` L112-123）が
効けば全レーン一律 `f(cap/5)` になり、legacy と**一致するはず**。なのに S1 で **−2.33%**、S3 で **−1.37%** ずれる。
差の大きさが「クリティカルがスコアに占める割合」（S1 は 71〜96%、S2 は 11〜20%）と順序一致なので、
**クリティカル注入の口径差**が第一容疑。ここを放置すると、以後の「改善した／悪化した」の判定が全部ぶれる。

## 1. タスク

### タスク0 再現と両口径の差の帰属確定（**最優先・読み取り専用**）

`tools/analyze_beat_score_models.ts`（legacy）と `tools/audit_hidden_cells_sim.ts`（既定 lanefans・
`tools/audit_hidden_cells.mjs` は L206 で `--mode=lanefans` を渡す）の**sim 合計の差**:

| | legacy | lanefans | 差 |
|---|---:|---:|---:|
| S1 | 116,829,040 | 114,162,150 | **−2,666,890（−2.33%）** |
| S2 | 74,895,810 | 74,669,710 | −226,100（−0.30%） |
| S3 | 78,485,270 | 77,425,702 | **−1,059,568（−1.37%）** |

やること:
1. 両ツールの **CASES / オプション差**を突き合わせて表にする（`audience` / `laneFans` / `maxCapacity` /
   `critFormat`（`beatMap`・`keys`・`beats`）/ `s3Fixes` / `mentalOverride` / `missedNotes` /
   `disabledSkillIds` / `goldenPhotoNames` / RNG）。
2. **満員ガードの実効を確認**: S1 `laneFans=[19,19,18,22,22]` 合計 100 = cap 100 → 満員、
   S3 `[8515,7748,8535,8518,6684]` 合計 40,000 = cap 40,000 → 満員。`src/formula/fan.ts` L112-123 が
   効いていれば全レーン `f(cap/5)` で legacy と一致するはず。**一致しない理由**を
   `src/sim/build.ts` L750-798 のログ（`laneFans=... → 満員/空席: [..]‰`）と実測 `fan.png` の
   スコアボーナス%で確定する。
3. 第一容疑（**クリティカル注入の口径差**）を検定する: S1・S3 は総スコアの 71〜96% が
   クリティカルセル（S2 は 11〜20%）で、差の順序と一致する。
   両ツールが注入する crit セル集合を dump して**差分セル数と総スコア差**を出す。
4. どちらが正しいかを**実測で**決める: 決着がつかない場合は「legacy = 受け入れ口径」を維持し、
   A10 監査側の口径を legacy に揃える（または両方併記）ことを提案としてまとめる。

**成果物**: `phase16_action12_mode_gap.md`（差の帰属表 + どちらが正しいかの裁定 + 根拠のファイル・行）

### タスク1 S2 の不足の内訳を source kind 別に確定（読み取り専用）

A10 監査出力（lanefans 口径）から読み取れる S2 の内訳:

- 実測 77,732,383 = Σpop(可読) 76,911,500 + 隠れ枠 820,883
- sim 74,669,710 = sim(可読セル) 74,377,095 + sim(隠れセル) 292,615
- つまり **不足 = 可読セル 2,534,405 + 隠れセル 528,268 = 3,062,673**

A11 は「beat 素点の不足 ≈1.33M」までしか出していない。**残り ≈1.2M がどの種類のセルか**を
`phase16_action11_decouple_out.json`（セル単位トレース）+ pop で source kind 別
（`beat` / `active` / `special` / `passive` / `photo` / `live_bonus`）に分解する。
**同一口径で**（タスク0 の裁定に従う。lanefans と legacy を混ぜない）行うこと。

### タスク2 隠れセルの**下側**ゲートの恒久化（A10 の宿題）

`tools/audit_hidden_cells.mjs` は上側（比 ≥2.0 = FAIL / 1.5〜2.0 = WARN）しか無い。
A10 で **S3 L3 = 0.04×**（sim 116,039 / 隠れ枠 2,635,445 = sim が実測の隠れ枠より大幅に少ない）が
記録されている。下側を追加する:

- 例: **比 ≤ 0.5 = WARN / 比 ≤ 0.25 = FAIL**（閾値は新設。**既存の上側閾値は絶対に緩めない**）
- 既存の上側判定と同じく photo-gate off/on・Σpop 口径の全組み合わせの最悪値で判定する
- S3 L3 が検出されることを確認し、他サンプルの下側比の一覧を出す（sim が実測より少ないレーンは
  「sim が実測を説明できていない」＝不足の在処の候補）

### タスク3 S4/S5 のレーンポップ遡及取得 → 15 観測を 25 観測へ（**撮影なし**）

`../aipura_nox/サンプル4/`・`サンプル5/` には `lane_pops_backfill.json` が**無い**（確認済み）。
すでに撮ってあるスクショから `prompts/backfill-lane-pops.md` の手順でレーン別ポップを遡及取得する
（**新規撮影は禁止**・既存ファイルは追記のみ・削除/改名禁止）。

そのうえで `phase16_action11_beatfit.ts` / `phase16_action11_weightfit.ts` を **5 サンプル**で回す。
観測が 15 → 25 に増えると「デッキ 3 属性」と「レーン識別子」の交絡が大きく緩むので、
**A11 で棄却した重み仮説が復活するか、棄却が確定するか**が決まる。

- 判定: 25 観測での LSQ rms がノイズ床（0.5%）近くまで落ちれば「重みが原因」で決着。
  2% 以上残るなら「式の形かレーン識別子」で決着（＝撮影依頼 §11 が必須になる）

### タスク4 クリティカル係数の段数集約則の裁定（A11 タスク3 の続き）

`src/formula/critical.ts` L19-42: `critFactor = 1500 + 50×stages + extras`。
A11 は「sim 2254（= 10 段）のセルだけ要求が ≈2383（≒12.6 段）」を観測したが、同層の他サンプルで
再現しなかったため断定を見送った。やること:

1. 全サンプル・全レーンで「同じレーン・同じ素点／b1／fan のビート」を crit セルと非クリセルに分け、
   **要求 crit 係数**（= `crit_sim × 比_非クリ ÷ 比_クリ`）を推定して表にする。
2. `critical_coeff_up` の段数の作り方（`src/timeline/buffs.ts` L151/L162/L196:
   `critical_coeff_up` と `critical_coeff_limit`（limitRelease）の**合算か最大か**、持続の満了境界）を
   候補ごとにシミュレートし、要求値の表を**唯一再現する組み合わせ**があるか調べる。
3. 唯一再現する組み合わせが見つかったら**それは機構の誤り**なのでタスク5 で修正する。
