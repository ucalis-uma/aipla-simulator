**読み取り時にこれらと矛盾した挙動を見つけたら、推測で補正せず記録し issues.md に上げること**
（サンプル間の矛盾が新仕様発見の最大の手がかりになる）:

1. **コンボ**: 成功ノートで +1。**コンボ継続バフなしの FAIL（A/SP/ビート MISS）で
   表示コンボ・全レーンのコンボがリセット**（サンプル1 b56: 55→0）。コンボ継続バフ保有中の
   FAIL はリセットされず表示コンボのみ +1（T5 b49）。ビートスコアの CB 基準 = 表示コンボ。
   ⇒ 画面の COMBO 値を**モデル近似せず画像どおり**全ビート記録する（リセットの検出に必須）
2. **強化効果延長・増強の量は「スキル毎・レベル毎」に定義された値**（固定値ではない。
   サンプル1 の「+7」はさらけ出す Lv2 の延長値にすぎず、「明記なしなら +1」も誤りだった。
   延長ビート数・増強段数は **ゲーム内マスタ（Info Pride API / 計算機リポジトリ vendor。
同一データ・下記「スキル効果データの参照」参照）のレベル別テキストで必ず確認**すること。
   マスタに無いフォトの延長/増強値はスクショから読む）。
   仕組みとして: 対象は各 BuffKey で残りビート最大のインスタンス、
   延長 = 残り時間に値を加算、増強 = 段階に値を加算
3. **対象選択**: 「ボーカル**タイプ**N人」= メンバーのタイプ（装着カードの属性）が一致するレーンを
   **レーン優先度順 L3>L2>L4>L1>L5** で先頭 N（ダンスレーンのメンバーがボーカルタイプ対象に
   なる=レーン属性とは独立）/「ボーカル**レーン**N人」= レーン属性一致レーンの**レーン番号順**先頭 N/
   「隣接」=左右隣接レーン/「センター」=L3/「スコアラータイプ」等 = 役割（role）基準
4. **「誰かがSPスキル発動前」**: SP ノート到来ビートの**前半**に発動（対象 = SPレーンへの事前バフ）。
   SP ノートのレーンが SP を発動できない（未所持・CT中・スタミナ不足）ときは成立しない
5. **`<サポータータイプのみ>` 等の装着制限**: ロール不一致のレーンでは常時不発
   （装着フォトのステータスは有効）。発動ログに載らない点に注意
6. **同名バフは1チップに合算**（段階合算）。バフ期間 = [発動ビート, 発動ビート+期間-1]
   （±1 のフレーム位相揺らぎあり）
7. **効果ボックス = 青ドット数と一致**（青ドット = スキル発動回数**ではない**）
8. **ノート種別ヘッダー行は全ビート不変の固定表示**（レーンのチャートタイプ: 多/SP+属性）。
   通常ノートのビート毎の有無はスコアポップの有無で判定する
9. **最終ビート等の「段階数が一斉に増える」表示**は終演演出ではなく増強/再付与で説明可能
   （サンプル1 b176 = 夏を先取りの3段階増強+自身への再付与）
10. **レーンカード上部の数字 = カードの強さ指標**（スコア計算に無関係・読まなくてよい）
11. **既知の未解決**（サンプル1 でも未解決のまま。新サンプルでも解けなければ【Unknown】）:
    HIT 94.1% 系の分母 / フォト詳細画面の表示消費値とライブ実消費の差
    （サンプル1: 表示 662 vs 実消費 681）/ 一部レーンのスタミナ消費 ±4〜5 の揺らぎ
12. **スタミナ読取の注意（S2 で確定・2026-09-02）**: current_stamina は数字 **7→2 の OCR 誤読**が
    出やすい（S2 で全レーン 236 行。系列に不連続な減少があったら元画像を必ず再確認）。
    また 1 ビート 1 スクショは「P 消費後・フォト消費前」の**中間フレーム**になり得る
    （フォトスキルもスタミナを消費する — 「フォトは消費されない」誤結論の原因になった実例）

### スキル効果データの参照（必須・スキルテキストのスクショは不要）

本サンプルには**スキルの効果テキストを撮影した専用スクショがない**が、必要ない。
ゲーム内マスタ（全491カード/全2043スキル・Lv1-6 の効果テキスト/スタミナ/CT を収録）は
**Info Pride（[IP]）と計算機リポジトリの vendor/（[MD]）の両方**が持っており、
内容は突合済みで同一（出典・更新状況・使ってよい範囲は `research/03_data_sources.md`
§2.1/§2.2 に記載）。手順:

1. **Info Pride API でスキルデータを取得**（curl または WebFetch・レスポンスは JSON）:
   - カード ID → スキル ID: `https://idoly-backend.outv.im/api/Card?id=<カードID>`
     （例: `?id=card-ski-05-waso-00` → `skillId1/2/3`）。
     カード ID は `deck.json` の `card_id` を使う（無い場合は `lane*_charactor.PNG` の
     カード名から `https://idoly-backend.outv.im/api/Card/List?level=230&rarity=10` で検索）
   - スキル ID → レベル別テキスト: `https://idoly-backend.outv.im/api/Skill?ids=<スキルID>`
     （カンマ区切りで複数可）。`levels[]` に Lv1-6 の `description`
     （延長/増強の値もテキストに含まれる）とスタミナ・CT が入る。
     **`deck.json` の `skill_levels` で指定されたレベルの行を使う**
     （例: さらけ出す Lv2 =「強化効果を7延長」・Lv4 =「10延長」）
2. **オフライン時・交差検証は計算機リポジトリのローカルマスタを使う**（同一データ）:
   `vendor/Skill.json`（`levels[].description` + `skillDetails[].efficacyId` の機械可読効果ID）/
   `data/skills_levels.json`（コンパクト形式・デコーダは `src/skillLevels.ts`）。
   スキル ID = card_id の `card-` を `sk-` に置換して接尾 `-1/-2/-3`
3. **画像との突合**: 画像で読めるスキル名・Lv・効果断片（バナー/効果ボックス）と、
   1-2 で確定したテキストが矛盾しないことを確認する。矛盾は issues.md へ
   （サンプル1 では夏を先取り Lv4 の「3段階増強」の読み飛ばしが後日の訂正につながった）
4. **フォトの延長ビート数・増強段数はマスタにない**（フォトスキルにレベル別
   テキストはないため）→ `photo_skill_*.PNG` のスクショから直接読む
5. **注意 — BWIKI 由来データ**: ローカルの info-pride clone
   （`Documents\idoly_pride\scratch\info-pride`）内の `data/wikiPages/cards.json` は
   BWIKI（中国版wiki）由来の部分収集データ（CN サーバー基準のため JP 実装カードの反映が
   遅れる・レベル別テキストなし）。**数値には使わない**（research/03 §2.2 の規約。
   GitHub 本体 info-pride 自体は週次更新の現役プロジェクトだが、スキルの数値マスタは
   vendor API 経由で取得する）

### `live_bonus.png` / `fan.png` の扱い（ステージ側パラメータ・必須記録）

この2枚はステージ側の計算パラメータの一次資料。**両方の内容を measured_data に書き込むこと**
（サンプル1 では撮影が無く来場者数が未検証のまま残った。撮影がある場合は必ず記録する）。

**`live_bonus.png`（ライブ詳細画面）から記録するもの**:

- ステージ名・STAGE番号・難易度 → `stages_index.json` の quest id（例: STAGE680 →
  `qt-tower-680`）を特定し `stage.id` として記録
- **ライブボーナスP**: 条件・効果テキスト・Lv・CT。**スキルマスタと照合する**
  （quest id が決まれば `data/live_bonuses.json` の `byQuest[questId]` に定義があるはず。
  例: STAGE680 =「誰かが消費スタミナ低下状態の時 ボーカルが高い2人に10段階スコア上昇[45]」
  Lv5・CT50）。画像とマスタが一致することを確認し、一致しなければ issues.md へ。
  シミュレータはこのテーブルを自動注入するため、json へは**照合結果**を書く
- **`live_bonus.png` が無い場合**: そのステージのライブボーナスは**計算に含めない**
  （マスタに定義があっても「画面で確認できた訳ではない」ため）。この場合
  `stage.live_bonus_check` に `"not_captured"` を書き、**summary と issues.md に
  「ライブボーナス未撮影のためライボなしで計算した（実際のライボが発動している場合
  スコアは実測より低く出る）」ことを必ず明記**してユーザーに知らせる
- 目標スコア（クリア報酬画面に表示される場合）→ `stage.target_score`

**`fan.png`（来場ファン数画面）から記録するもの**:

- **個人（レーン平均）来場数** → `stage.audience`。**レーン別「来場ファン数」5件の平均**を入れる
  （= 見出しの合計来場数 ÷ 5。例: S2 は合計 66,031 → `audience: 13206`）
  - ⚠️ **見出しの合計来場数をそのまま入れると 5 倍過大**になる（`audience` は **個人（レーン平均）来場数**
    として `data/stages/audience_advantage.json` を直接引く。`src/formula/fan.ts: fanBonusPermil`。
    例: 20人 → 1002‰（+0.2%）/ 8,000人 → 1375‰ / 16,000人 → 1620‰ / 50,000人以上 → 2000‰ で頭打ち）
  - 満席の会場では `audience = capacity/5` でよい（S1: 100人席 → 20人 → +0.2%）。人数が読み取れない場合は
    `audience` を省略 or `null` + 注記（`src/cli/simulate.ts` が会場キャパ/5 から導出する）
  - 見出しの注記「**スコアボーナス ※最大+X%**」＝ `表引き(capacity/5)`（S2 +58.0% = f(14,000)／
    S1 +0.2% = f(20)／T5 +62.0% = f(16,000)）。**レーン別の値ではない**のでレーン平均と取り違えないこと
  - ⚠️ **`audience` に目標スコアを入れないこと（2026-09-30 追記・サンプル1 で実害発生）**:
    サンプル1 の `deck.json` は `audience: 71000` だったが、71,000 は当時の画面左上の
    **目標スコア**（`18,780,790/71,000` の右辺 = `qt-area-1-001` の `clear`）で、会場キャパは 100 人だった。
    fan は 2000‰（テーブル上限）に化けて全スコアが約 2.27 倍になり（+127% 乖離）、以後の解析を誤誘導した。
    記録するのは **fan.png の「来場ファン数」の数字だけ**。
    **受け入れ検査: `node tools/audit_audience.mjs`**（宣言 audience × fan‰ × cap × cap/5 を一覧化し、
    「宣言値 == 目標スコア」「宣言値 > 会場キャパ」を NG として指摘する）
- **レーン別**: ファン数（総ファン）・コアファン率・**来場ファン数**・**スコアボーナス%**・**スキル成功率**
  → `stage.lane_fans[]`（下記スキーマ）として全レーン記録。**これは必須**（2026-09-30 追記）:
  ゲーム側のボーナスは**そのレーンの来場数で決まる**。S2 ではレーン別表示
  +53.9 / +57.0 / +57.4 / +56.5 / +56.9% が表引き値 539 / 570 / 574 / 565 / 569‰ と **5/5 完全一致**した。
  現行エンジンは `audience` 1値（＝レーン平均）を全レーンへ適用する近似で、レーン間の相対差は最大 2.2%
  出る（合計スコアへの影響は小）。詳細 `research/23_beat_score_analysis/phase16_action3_fan_per_lane.md`
  - 参考: ゲーム側の個人来場数の上限は会場キャパの 1/5（S3 の fan.png 実測 8,000 = 40,000/5 と完全一致）
- 目標スコア → `stage.target_score`（**`audience` とは別キー**）

## 4. リプレイ画面の構造（座標は必ず自分で再計測してから一括処理へ）

1 枚（例: `lane3\beat_060.PNG`）に以下が入る（サンプル1 1080×1920 の構成。T5 は 1668×2420 で
**画面解像度・UI 配置がサンプル毎に異なるため座標の持ち回りは不可**。読取技法だけ継承すること）:

- **左上**: 累積スコア `18,780,790/71,000`（= 全レーン合計の累積 / 目標スコア）
- **右上**: `COMBO 4 RANK S+27`（COMBO = ヒット済みノート数。ビート数 ≠ コンボ数。
  **リセット譜面ではビートとコンボが乖離する**）
- **注目レーンカード**: アイドル名・現在ステータス値（バフ込み表示値）・スタミナ `現在/最大`
- **スコアポップ**（レーンカード右上）: このビートのこのレーンの獲得スコア。
  **黄色 = CRITICAL / 白 = 通常**。省略表示（+38.6K 等）。
  **【最重要・2026-09-05 追加】各レーンのポップ数字（+38.6K 等）は全ビート×全レーンで必ず
  記録する**（`gained_score_pop.color` とセットで `gained_score_pop.text` へ。読めないときのみ
  null + 理由）。K 単位の省略表示のままでよい（±0.1K 分解能 = 乱数解析に十分）。
  ポップ数字が**遮蔽・非表示**のレーンは `null` + 理由（"遮蔽" / "pop なし"）を記録。
  **レーン別ポップは λ（基本係数）・off-attr 扱い・フォト重複規則をレーン単位で一意に決める
  一次データ**（research/23 pack_v2/05 参照。5 レーン合計では各レーンの乱数が平均化され、
  これらの検証は不可能）。ポップが写っていないビートの正確値は累積スコアの差分で求めるが、
  これはレーン別内訳の代用には**ならない**（合計値であることに注意）
- **現在の効果ボックス**: フォーカス中レーンの発動中バフ（`10段階 クリティカル率上昇` 等）。
  表示行数でクリップされる可能性 → 隠れ分は下段カードのバフアイコンで裏取り、不明は【Unknown】
- **ノート種別ヘッダー行**: 全ビート不変の固定表示（レーンのチャートタイプ）
- **BEAT 数字**: 現在のビート番号。**ファイル名 beat_NNN と一致することを全件検証**
  （撮影飛び・重複の検出になる）
- **下段 5 レーンのカード**: 全レーンのバフアイコン + 数字バッジ（残りビート数）+
  **青ドット = そのレーンが受けているスキルバフの個数**（効果ボックスのチップ数と一致）

## 5. 読み取り規約（サンプル1 の教訓を含む）

1. **発動ログの重複検知**: 同一発動が 2 フレームに写ることがある（サンプル1 では o1=b0 が
   o3=b1 の重複で実発動数が 1 少なかった）。スタミナ消費値・発動前後の状態で各 order を照合し、
   重複は明記した上で統合する（`実発動数 N 件（記録 M 件）`）
2. **スキル内容は「スキル名 × レベル」でゲーム内マスタ（Info Pride API / vendor）から確定する**: 発動バナー
   （skill_order）やスキル画面のスキル名・Lv を基に、上記「スキル効果データの参照」の
   手順でレベル別効果内容（%値・段数・[Nビート]・延長ビート数・増強段数）を確定する。
   バナーに写ったテキスト断片と矛盾しないか照合し、不一致は issues.md へ
   （サンプル1 では夏を先取り Lv4 の「3段階増強」の読み飛ばしが後日の訂正につながった）。
   スクショからの読み取りはフォトスキルのみでよい
3. **スタミナは max 値照合で自己検証**（`research/08` §1.2）。全フレーム current ≤ max を確認
4. **コンボは画面値をそのまま**（近似禁止。リセットの発見が新仕様になる）
5. **マイフォトは表示消費とライブ実消費を両方記録**（差分の検証継続）
6. **来場者数・レーン別スコアボーナス/成功率は `fan.png` から記録する**（無い場合のみ
   「画像では未検証」と明記。捏造禁止）
7. 中間生成物（クロップ画像・スクリプト）は `サンプルN\analysis\` 配下に置く
