   実測根拠を持たない推測だった場合は、根拠をコメントに書いて更新する
5. **データの変更は importer 経由**: `data/` の生成物を直接編集しない。`npm run build:data:ext`
6. UI 変更時は `npm run build:ui`（UI へのデータ埋め込みは `tools/build_ui.mjs` の規約に従う）
7. **実測データの捏造・補間禁止**: measured_data に `null`/【Unknown】がある箇所は
   推測で埋めず、近似なら【Estimate】タグ + 検証結果を残す
8. **ユーザーの手書き計算式がカルテの正（最重要・2026-09-02 で確定した作業方法）**:
   乖離の原因を考えるとき、ユーザーが今回のような計算式（JHTV5213 型:
   ステータス×パワー%×B1×クリ×ファン×B2×乱数 + 写真固定値・A/SP 別の内訳）を
   示してくれたら、**その式の形にモデルを揃えるのが最短**。逆算式が 0.95〜1.05 に収まれば
   乱数（±5%）で両立したと判断してよい
9. **数値フィットは事実ではない**: ある規則で数値が合う＝仮説。**技能文・ユーザー逆算式・docs の
   いずれかと矛盾する規則は即座に破棄**して実装しない（2026-09-02 の実例: 「千紗ビームは
   L4 自身にも csu-6 付与して B2 が上がる」説は計算上 b40/b130 が ±5% 内に入ったが、
   技能文が「隣接するアイドルに」で明確に否定 → ユーザー指摘で破棄。フィット係数を
   盛り込みたくなる誘惑に勝つこと）
10. **係数を捻じ曲げるより先に「欠落項」を探す**: ユーザー式に「+47,601+62,833」のような
    画像由来の加算項が現れたら**写真/装備の固定値加算**を疑う（見逃していた項）。
    2026-09-02 の決め手は「写真の Aスコア固定値の平坦加算」（A スコアには
    Σ(写真 structured a_score の fixed 値) が加算される）だった
11. **出力規律（プロジェクト最優先）**: 長い調査・修正作業では**完了までチャットへのテキスト
    出力でターンを終了しない**（進捗レポート・中間報告・「最終出力」の語も途中で禁止 —
    完了したかのように誤解される）。途中結果は research/・JSON・ログ・todo に記録する。
    ユーザーから進捗を聞かれた場合のみ簡潔に回答して作業に戻る。撮影/動画は不要と明言
    されたら画像解析を要求しない（現にあるデータで進める）
12. **OCR の信頼度**: 効果パネル・段数・数値は信頼可。スキル名は誤読あり
    （「キャンピーム」= 千紗ビーム 等）。画像の「ステータス」表示は A スキル発動後
    （自身バフ適用後）の値が写るため、**スコア計算に使うのは PRE（適用前）**を確認する
13. **スタミナ 7→2 の OCR 誤読パターン（2026-09-02 確定）**: current_stamina の「7」始まりが
    「2」に誤読されることがある（S2 で全レーン 236 行）。「実在しない謎減少」はまず
    元画像の目視確認で誤読を疑う（**ユーザーから OCR 修正の許可が出た場合のみ**
    修正表を aipura_nox 側に追記・元ファイル自体は不変）。
    発動前後のスクショは P 消費後・フォト消費前の**中間フレーム**のことがある
    （「フォトがスタミナを消費しない」という誤結論の原因になった実例）

### 3-4. 乖離の定量分析（確定仕様実装後も残る差分）

1. 再取得: `npx tsx src/cli/simulate.ts --input examples/sampleN.json --n 0 --crit-rate 0 --out %TEMP%\sampleN_after.json`
2. before/after と実測を **ビート単位で突合**:
   - 実測 timeline の各ビート `beat_gained_score`（累積差分）とシミュの `confirmed.timeline` を比較し、
     **乖離が始まる最初のビート・最初のスキル**を特定する
   - レーン別内訳・発動スケジュール（activations のビート/レーン/種別）の一致率を出す
3. 残余差分の要因候補を**この順で**検証する:
   - **ユーザー式との突合**: ユーザーが計算式を提示してきたら、その形に合わせて
     モデルを分解・揃える（鉄則 8）。イベント単体の必要倍率 = 実測 ÷ (basic×power×b1×combo×fan×crit)
     を出し、±5% なら乱数で両立
   - **欠落項**: 必要倍率が ±5% を外れる場合、まず「加算されるべき項が抜けていないか」
     （写真の Aスコア固定値・エール/フォトの % ・B2 の csu の掛け方 等）を探す（鉄則 10）。
     係数や参照先を捻じ曲げる規則は技能文に矛盾しないかを必ず確認（鉄則 9）
   - クリティカル: 実測 CRITICAL 率で `--crit-rate <実測値>` の Monte Carlo（`--n 1000`）を回し、
     実測スコアが分布内に収まるか。**クリティカルはレーン（メンバー）ごとに独立ロール**。
     **measured_data に critical_flags（ビート別 crit 有無）がある場合はフラグをそのまま
     シミュに再現させる「再現ラン」が最強の検証になる**（S2 で採用: 乱数を消して
     ビート単位の残差が直接見える。レーン別比率が ±5% 内なら両立と判定）
   - **ccu（クリティカル係数上昇）の系列確認**: crit 乖離の分析では
     「ビートごとの必要 critF = 実測 ÷ (basic×power×b1×combo×fan) − extras」を逆算し、
     その差分から ccu 段数を復元する（critF = 1500 + 50×ccu + extras）。段数系列が
     スキル発火スケジュールと整合するかを必ず確認（S2 実例: b41 ccu13→critF 2504・
     b100 ccu0→1854・b142 ccu8→2254 の完全一致。ccu 系列が誤ると必要傾きが
     出ず他の要因に誤認する — 第一段階の教訓）
   - スコアモデル差分: confirmed（crit なし）ですでに実測を大きく上回る場合、
     バフ段数・CB 係数・SkillPower・B1 などの**基礎モデルの過大評価**を疑う
     （クリティカルは加点なので、crit 込み実測 < crit なしシミュの乖離は基礎モデル由来）
   - HIT 94.1% 分母の未解決（MISS 0 でもポップ数 ≠ ノート数の謎）・
     **スタミナ消費の表示/実測ズレ（S1/T5 で既知の残課題・スコアには影響しない）**
4. **過学習の禁止**: 特定サンプル専用の分岐や数値の直接埋め込みはしない。
   修正は必ず「仕様」の形（全サンプルで共通に振る舞う規則）として実装する

  **OCR 誤読の修正は例外**: ユーザーが明示的に許可した場合（2026-09-02 の実例:
  「OCRエラーは自分で元画像解析して修正しても構いません」）は、元画像を目視確認した上で
  修正表 JSON を aipura_nox 側に**追記**してよい（元ファイルの削除・改名・上書きは禁止）
- わからない仕様の実装を後回しにして全体を完成させることを優先し、
  保留した仕様は【Unknown】で記録する（部分一致より過剰近似のほうが害が大きい）
- **画像解析は「そのビートの計算に使った値」を確定させるのが目的**。
  効果パネルは発動後の値が写る（PRE が正しい）ことに注意し、必要なら
  前後のビート・所持バフから逆算する
